EsiNet Schema Scripting

Developed a Python workflow that parses locally maintained critical GIS data, including address points and road centerlines, and transforms it into schemas that conform to NENA gu idelines used for Intrado EsiNet uploads. The script preserves the locality's existing internal schema while generating new, properly formatted shapefiles for submission.

NG9-1-1 Data Management Emergency Response Critical Data NENA

PROJECT OVERVIEW

Why this was necessary

Preparing these datasets previously required repetitive manual field mapping and formatting to meet NENA requirements. The automated workflow reduces that process to a few scripted steps launched through BAT files, producing standardized, submission-ready shapefiles consistently and efficiently.

WORKFLOW

How it works

  1. Maintain accurate local GIS data.
    Maintain authoritative address point and road centerline data to a high level of accuracy before beginning the conversion process.
  2. Review NENA requirements.
    Review the applicable NENA guidelines for the dataset being processed to identify the required schema, fields, formatting, and attribute requirements.
  3. Transform the data.
    Run the Python field-mapping workflow to translate the locally maintained schema into the required NENA format and generate new shapefiles in a dedicated output location.
  4. Package and submit.
    Package the resulting shapefiles into the required ZIP format and upload the completed datasets to the EsiNet portal for validation and submission.

RESULT

Lessons

Uniform formatting of your unit types / numbering system will save you a headache when parsing a large number of addresses.

02

Break local addresses into components

Rather than requiring the locality to completely redesign its existing address schema, Python parses the maintained full-address value into individual components such as address number prefixes, numbers, suffixes, street names, directions, and units.

Translate local records into NENA fields

ArcPy reads each authoritative address point, parses the locally maintained values, and maps the resulting components into the standardized output fields. This allows the source GIS data to remain structured for local operational needs while producing a separate submission-ready dataset.

05

Generate the submission-ready shapefile

After the attributes are transformed, the output is clipped to the appropriate jurisdictional extent, projected to WGS 84, and exported as a shapefile into a date-organized upload directory. The resulting dataset is ready for packaging and submission through the EsiNet workflow.

Companion workflow — NENA_RCLs: The road-centerline workflow uses the same overall concept but applies it to roadway-specific information, including left and right address ranges, parity, street-name components, postal communities, one-way values, speed limits, and other road attributes before producing the standardized RCL submission dataset.
