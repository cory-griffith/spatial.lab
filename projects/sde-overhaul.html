SDE Migration + Overhaul

Modernized the enterprise GIS catalog by inventorying existing datasets, standardizing schemas, and migrating authoritative layers into a new ArcGIS Server and enterprise database environment.

DBMS Schema Enterprise Migration

PROJECT OVERVIEW

Why this was necessary

With the legacy ArcGIS Server 10.4.1 environment reaching end-of-life, the migration to a new ArcGIS Enterprise 11.5 environment provided an opportunity to rebuild the GIS catalog from the ground up, standardizing schemas and improving data organization and usability across the organization.

REFLECTION

Lessons

Understand your DBMS before rushing the configuration of the features within. I wish I would have understood the field formatting and comprehend the schema ownership and permissions of PostgreSQL before I started the migration. I spent a lot of time troubleshooting issues that could have been avoided if I had a better understanding of the database management system.

Try to break things early, as long as the old DBMS is functional. I should have pushed the limits and played around with the configuration of the new DBMS before I started the migration. This is not necessary, but I was not used to this DBMS so I was a bit timid in my approach. It worked out, and I am quite comfortable with the software now but I was thinking I bit off more than I could chew in the beginning.

I would suggest documenting anything and everything regarding the schema of your GIS data. I believe I did a good job of creating uniform fields for some of the "non-essential" fields, but the more eyes on the project certainly the better the outcome.

All in all, I would be comfortable doing something of this magnitude again. I am glad I had the opportunity to customize my environment and configure items to a format that I am comfortable with.

RESULTS

Outcome

The migration was successfully completed from a SQL Server-based GIS environment to PostgreSQL and a newly configured ArcGIS Enterprise architecture. Existing enterprise geodatabase content was exported using XML workspace documents, providing a controlled source for migrating legacy data into the redesigned environment. A local file geodatabase was also maintained from this export, allowing legacy records to be appended into newly created feature classes where significant schema changes prevented a direct migration.

The new GIS catalog was first constructed within the DEV enterprise geodatabase. Using the catalog design documented in Excel as the reference, I created the required feature datasets and feature classes, applied standardized naming conventions, configured domains, and implemented the redesigned schemas. Python automation was also used to assist with creating and organizing the new dataset structure, reducing repetitive manual configuration during the rebuild.

Once the new catalog and schemas were established, legacy data was systematically appended into the appropriate feature classes and validated against the new structure. This allowed datasets requiring substantial schema changes to be properly rebuilt rather than simply carrying legacy structures and inconsistencies into the new environment.

The database architecture was also redesigned around specific operational purposes. DEV serves as the primary development and data-management environment and utilizes one-way replication to maintain the PROD enterprise geodatabase. This provides a cleaner workflow for implementing and validating changes before they reach the production environment.

A separate enterprise geodatabase was configured specifically to support REST services used by the organization's permitting web application. Rather than housing the entire enterprise GIS catalog, this database contains only the key feature classes required by the application and receives its data through replication from DEV. The database was also registered with ArcGIS Server Manager to support publishing and maintaining the required web services.

An additional enterprise geodatabase was provisioned as expandable infrastructure for future web applications, specialized datasets, or archival purposes. This provides flexibility for the GIS architecture to grow without requiring another major database restructuring as new applications and requirements are introduced.

The project also required developing practical PostgreSQL administration skills throughout the migration. PostgreSQL was selected in part to reduce the licensing costs associated with SQL Server Enterprise while still providing a supported enterprise geodatabase platform. The transition required adapting to PostgreSQL-specific conventions, including differences in database domains and its preference for lowercase identifiers, but the overall migration has proven stable and successful.

Ultimately, the project went beyond simply migrating GIS data from one server to another. It resulted in a rebuilt and standardized GIS catalog, a more deliberate DEV-to-PROD workflow, application-specific database separation, improved schema consistency, and an enterprise database architecture designed to support future GIS services and applications.
