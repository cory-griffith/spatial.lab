Vision Real Estate & Parcel Integration

Developed a complex SQL query to retrieve current real estate information directly from the Vision database and associate it with the locality's parcel GIS data. This integration provides GIS users with ac cess to up-to-date property information while maintaining the parcel layer as the spatial foundation.

SQL Vision Joins

PROJECT OVERVIEW

Why this was necessary

This integration was necessary following the Real Estate Department's migration from the legacy CAMRA system to Vision. A new SQL query was developed to retrieve the relevant property information from Vision and align it with the existing fields associated with the locality's parcel data.

Without this integration, the parcel layer would contain geometry but lack much of the descriptive real estate information users rely on. The query restores that connection, allowing users to access current property information directly through the GIS parcel layer.

WORKFLOW

How it works

  1. Review the Vision data structure.
    Review the available Vision field documentation to understand how real estate information is stored and identify the attributes needed for GIS integration.
  2. Evaluate existing database views.
    Review the established SQL Server views to better understand existing table relationships, available fields, and how information is organized across the Real Estate database.
  3. Develop and test the SQL query.
    Query the necessary databases and progressively build the required dataset. Through iterative testing, refine joins, fields, and conditions until the results accurately represent the desired real estate information.
  4. Establish the parcel relationship.
    Identify a common key field between the Vision records and the authoritative parcel feature class, allowing the resulting real estate information to be reliably joined to its corresponding parcel geometry.
  5. Implement the production workflow.
    Finalize the query and establish a repeatable workflow that maintains the connection between current Vision records and GIS parcel data, providing users with access to up-to-date property information.
Design note:Utilize the vendor for questions as much as possible, as they have a better understanding of the database structure.

SQL WALKTHROUGH

How the Vision real estate integration works

The full production query contains additional joins, fields, and transformation logic. The excerpts below highlight several of the key techniques used to translate live Vision real estate information into a structure that can be associated with the GIS parcel dataset.

vision_ssms.sql — Translate Source Fields 
SELECT
              rpr.REM_PID AS MRECNO,
              rpr.REM_GIS_ID AS GIS_ID,

              LTRIM(
                  RTRIM(rpr.REM_ALT_PRCL_ID)
              ) AS MMAP,

              rpr.REM_LEGAL_AREA AS [MACRE#],
              rpr.REM_PARCEL_STATUS AS PARSTAT
01

Translate Vision into the existing GIS structure

Vision uses a different field structure than the previous real estate system and the existing GIS parcel workflow. Selected source fields are renamed and cleaned within SQL so the resulting dataset aligns with the field names and information already expected by downstream GIS processes.

vision_ssms.sql — Connect Related Records 
FROM REAL_PROP_REALMAST rpr

          LEFT JOIN REAL_PROP_ADDRESS rpa
              ON rpr.REM_PID = rpa.ADR_PID

          LEFT JOIN REAL_PROP_PARCEL rpp
              ON rpr.REM_PID = rpp.PRC_PID

          LEFT JOIN REAL_PROP_LAND rpl
              ON rpr.REM_PID = rpl.LND_PID
02

Combine information from multiple tables

The required property information does not exist in a single Vision table. SQL joins connect the master property record with related address, parcel, land, ownership, sale, and building information using their established relational keys.

vision_ssms.sql — Clean Sale History Values 
NULLIF(
              LTRIM(
                  RTRIM(
                      CASE
                          WHEN sh.book_clean LIKE 'WF%'
                              THEN NULL
                          ELSE sh.book_clean
                      END
                  )
              ),
              ''
          ) AS MINTYR
03

Normalize inconsistent property records

Some real estate values require conditional processing before they are useful to GIS. CASE, NULLIF, and string-cleaning functions are used to evaluate source values, remove unwanted placeholders, and return consistent results for the parcel dataset.

vision_ssms.sql — Consolidate Building Information 
COALESCE(
              cdm.CNS_STORIES,
              cdu.CNS_STORIES,
              com.CNS_STORIES,
              res.CNS_STORIES
          ) AS [MSTOR#]

          COALESCE(
              res.CNS_FOUNDATION_DESC,
              cdm.CNS_FOUNDATION_DESC,
              com.CNS_USRFLD_210_DESC
          ) AS MFOUND
04

Consolidate multiple property types

Building characteristics can be stored in different source tables depending on the type of property being evaluated. COALESCE allows the query to check multiple potential sources and return the first available value into one consistent GIS field.

vision_ssms.sql — Limit the Final Dataset 
WHERE
              rpr.REM_PARCEL_STATUS = 'A'

              AND rps.SLH_CURRENT_OWNER = 1

              AND rpl.LND_LINE_NUM = 1

              AND rpl.LND_BLDG_NUM = 1
05

Return the appropriate property records

The final query applies business rules to prevent unnecessary or duplicate records from entering the GIS workflow. The result is limited to the property, ownership, land, and building records required for the parcel integration.

Production query: The complete SQL implementation contains additional field mappings, joins, sale-history logic, ownership information, building attributes, and supporting records that are intentionally not reproduced on this portfolio page.
